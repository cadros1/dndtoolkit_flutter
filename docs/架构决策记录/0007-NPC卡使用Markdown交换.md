# ADR-0007：NPC 卡使用 Markdown 交换

## 背景

计划中的 NPC 卡包含大量自由文本、重复的特性与动作条目，并需要在 Windows、Android 和模组资料整理流程之间交换。JSON 适合内部保存，但不适合直接分发和人工阅读；现有角色专用 PDF 的固定字段也不适合 NPC 的可变长内容。

用户还可能导入由其他工具或人工编写的 Markdown，因此导入不能只处理应用原样导出的文件，但也不能把猜测结果静默保存成缺失大量数据的 NPC 卡。

## 决策

- NPC 卡使用 Markdown 作为计划交换格式，一个文件只保存一张 NPC 卡模板。
- 应用导出的文件使用 UTF-8，并在头部写入两个非中文机器字段：
  - `DnDToolkit-NPC`：格式标识及格式版本。
  - `SHA256`：内容校验值，使用 64 位小写十六进制表示。
- 除上述两个机器字段外，字段名、标题和分区名均使用当前中文 UI 术语，保证直接阅读和分发时不依赖应用。
- SHA-256 的规范输入为：将换行统一为 LF 后，移除头部 `SHA256` 字段所在整行的其余完整 Markdown UTF-8 文本。格式标识和所有 NPC 内容均参与校验，校验值字段本身不参与，以避免自引用。
- 任何空格、换行或文本编辑只要改变规范输入，就会使校验值不一致。实现必须通过固定 fixture 覆盖 LF、CRLF、中文、多行文本和空字段。
- 文件不保存内部 NPC ID，也不保存实例、当前/临时生命值、先攻、集群、当前遭遇或云端信息。导入总是创建新 NPC 卡，不按名称覆盖。

## 导入顺序

1. 先检查 `DnDToolkit-NPC` 格式标识。
2. 有受支持标识时，按上述规范重新计算 SHA-256。
3. 校验一致时按应用格式解析，并显示正常导入摘要。
4. 校验不一致时明确提示“文件在导出后被修改”，继续尽力解析，在确认前列出缺失、变化和无法识别的内容。
5. 没有受支持标识时，视为任意 Markdown，根据中文标题、表格和常见文本结构尽力识别，并强制显示预览和未识别内容。
6. 无法得到有意义 NPC 内容时拒绝保存；多个文件中一个失败不得阻止其他文件继续预览和导入。

格式标识只声明文件声称采用本应用格式。SHA-256 是无密钥校验，不是数字签名；任何人都可以修改内容后重新计算校验值，因此它不能证明文件来源可信、没有恶意内容或确实由官方应用生成。用户文案只能描述为“与文件记录的校验值一致/不一致”，不能描述为身份认证或安全验证。

## 结果

优点：

- 应用导出的 NPC 卡可直接阅读、编辑和分发。
- 未修改的应用文件有确定的完整性检查路径。
- 修改过的应用文件和任意 Markdown 仍有尽力恢复入口。
- 长文本和数量不固定的特性、动作比固定 PDF 字段更自然。

代价：

- 任意 Markdown 识别必然存在歧义，需要预览、警告和恢复路径。
- 中文标题和格式演进会成为兼容契约，未来改名必须保留旧格式读取。
- 换行和字段规范必须通过 fixture 固定，否则不同编辑器可能造成不必要的“已修改”提示。
- SHA-256 不提供来源认证，不能替代签名或信任模型。

## 被拒绝的方案

- 只导入应用原样导出的 Markdown：无法满足整理和迁移已有模组资料的需求。
- 对任意 Markdown 静默自动保存：容易产生字段错位和数据丢失。
- 复用角色专用 PDF：固定表单无法自然容纳可变数量的 NPC 特性与动作。
- 只提供 JSON：不利于直接阅读、人工编辑和模组分发。
