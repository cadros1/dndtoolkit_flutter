# AI 建卡

## 定位与边界

AI 建卡只用于创建新角色。它不会编辑已有角色，也不会给角色 JSON 增加 AI 来源字段。最终结果是普通的内存中 `Character`，进入现有编辑器；只有用户点击“保存并退出”才写入本地主要副本。

该功能是可选联网增强。首次进入时必须确认输入会发送到第三方、可能产生费用、生成范围仅为 D&D 5E 2014 官方常规内容。AI 不能被应用完整验证，最终构筑、规则和数值仍由用户复核。

从建卡页返回时必须二次确认。确认退出会取消正在进行的请求，并丢弃本页面的表单、构筑方案和阶段草稿。

## AI 服务配置

用户保存具名 DeepSeek 或 OpenAI 协议配置，包括 Base URL、模型、思考开关和强度。配置元数据位于普通偏好，API Key 以配置 UUID 为键保存在系统安全存储。

请求使用 `/chat/completions` 与 JSON object 模式，不发送温度或 token 上限。角色生成请求的客户端超时为 10 分钟，以容纳较慢的推理模型；模型列表请求仍为 30 秒，连接测试为 2 分钟。连接测试、四阶段系统提示、修复提示和动态说明均使用中文，集中位于 `lib/services/ai_character_prompts.dart`。API Key、完整提示词、响应和思考内容不进入日志或本地文件。

## 输入与属性生成

总等级、AI 配置、属性生成方式和玩法偏好必填。建卡要求分两种模式：

- “从你的想法生成”：用户填写角色描述，AI 在构筑方案阶段选择姓名、阵营、职业、种族和背景。
- 明确选择：姓名、职业、种族、背景和阵营均是不可替换的硬约束。

属性方式包括购点、本地 `4d6dl1` 掷骰、给定点数组和标准数组。AI 只分配基础值并给出种族调整与职业等级实际授予的属性提升；最终值由本地逐项相加。购点预算、数组多重集与最终范围由本地校验。

人物塑造继续按外貌与个性背景两个完整组控制。外貌组包括年龄、身高、体重、眼睛、皮肤、头发和附加特征；附加特征不属于个性背景组。组由用户填写时保留原文且不发送给第四阶段；开启该组的“从你的想法生成”时只发送对应倾向；“无需添加”时保持为空。角色经历属于第四阶段叙事契约，可以由 AI 生成，也可以保留用户原文。

## 四阶段流程

### 1. 设计构筑方案

第一阶段按建卡模式选择两套互斥提示词和请求数据。明确选择只要求 AI 整理用户给定的职业、种族与背景并总结定位；自由生成才要求 AI 决定姓名、阵营、职业、种族、背景及定位。两种模式均会生成构筑思路。模型不会收到另一模式的说明或数据。

用户必须在分项对话框中确认。总等级只读；职业名称、等级、子职、种族、背景和两类定位均可修改；自由生成的姓名与阵营也在此确认。修改后的方案完全覆盖 AI 原方案，职业等级之和必须等于总等级。后续阶段不能改变已确认方案。

### 2. 细化构筑方案

AI 生成基础属性分配、种族调整、属性提升或专长、熟练项、装备、武器、钱币、法术和当前等级已取得的特性。

- 职业、子职、种族、背景和专长特性，专精、战斗风格及职业资源统一写入“特殊能力”。
- “其它攻击/法术备注”只保存武器或法术列表无法表达的攻击与施法补充。
- 专精不改变现有检定模型；玩家在检定中心使用额外加值处理。
- 角色资源仍通过自由文本由用户管理。

所有阶段共享构筑原则：硬约束优先；属性优先形成有收益的偶数；属性提升按实际职业等级取得；无明确收益时优先单职业；兼职应满足前提、避免无意义延迟核心能力，并优先共享主要属性。角色卡和 PDF 只支持一套结构化施法信息；用户强制指定不同施法属性兼职时保留选择并提示风险，结构化施法信息使用主要或投入等级最高的施法职业。

### 3. 计算衍生数值

AI 只生成应用无法可靠推导的完整最终值：经验、被动察觉、护甲等级、先攻、速度、最大生命值、总生命骰、法术位、法术 DC、法术攻击、武器命中与伤害，以及特性中的资源次数、骰型和范围等数值补充。

AI 同时返回结构化数值组成。应用检查每项“基础值 + 调整项 = 最终值”、最终值与角色字段相等、法术位环级唯一，以及武器顺序和数量一致。应用不验证模型所依据的具体职业或装备规则是否正确。

熟练加值、属性调整值、普通属性/豁免/技能检定基础加值由本地处理。当前 HP、当前生命骰和剩余法术位初始化为满值；临时 HP 为 0；死亡豁免均未勾选；法术表补齐固定空位。

### 4. 塑造人物

第四阶段只负责用户交给 AI 的外貌和人物设定。它按“仅外貌”“仅人物设定”“两者同时”选择三套互斥提示词及最小响应字段，不发送开关、模式标识、用户原文、姓名或不需要生成的另一组字段。两组都未交给 AI 时，无论建卡模式为何都跳过第四次请求，因此一次建卡通常产生 3–4 次请求。

全部阶段完成后，应用不再单独展示属性分配结果，而是提示 AI 角色卡可能包含错误。用户确认已知晓后进入现有角色编辑器，人工检查角色卡并与 DM 沟通。

## 失败与恢复

每个阶段拥有独立固定 schema、白名单解析和一次完整修复请求；第一阶段的两套模式与第四阶段的三种生成范围各自使用对应的最小 schema。共同规则集中拼接一次，不在每段阶段提示中重复。页面展示当前阶段、总进度和本次实际生成用时；构筑方案等待用户确认期间暂停计时。修复仍失败时保留表单、已掷数组、确认方案和已成功阶段；用户可从失败阶段重试，不重复调用前序阶段。

模型不能提供角色 UUID、路径、更新时间、玩家名、画像或 API 配置。最终白名单组装本地生成 UUID 和熟练加值，并保持现有角色 JSON、PDF 与云端备份契约不变。
