# 开发、构建与发布

## 当前工具链约束

- Flutter：stable channel 项目；实际使用版本应以 `flutter --version` 和 `.metadata` 为准。
- Dart SDK：`pubspec.yaml` 要求 `^3.10.1`。
- Android Java/Kotlin target：Java 17。
- Node.js 只用于 Husky 与 commitlint，不参与 Flutter 运行时。
- 依赖版本以 `pubspec.lock` 和 `package-lock.json` 为可复现基线。

不要只依据 README 中宽泛的“Flutter 3.x”判断兼容性。

## 初始化

```powershell
flutter --version
flutter doctor -v
flutter pub get
npm install
```

如果只修改 Flutter 代码且 Husky 已安装，通常不需要重复执行 `npm install`。

## 代码生成

`lib/models/character.g.dart` 由 `json_serializable` 生成：

```powershell
dart run build_runner build --delete-conflicting-outputs
```

修改 `@JsonSerializable` class、构造参数或 `@JsonKey` 后必须重新生成并检查 diff。禁止手工修补 `.g.dart`。

## 日常质量命令

```powershell
dart format --set-exit-if-changed lib test
flutter analyze
flutter test
```

提交信息通过 Husky 调用 commitlint，采用 Conventional Commits 风格，例如：

```text
feat(adventure): add roll history export
fix(sync): preserve local portrait on download
docs: document character schema compatibility
```

## 本地运行

```powershell
flutter run -d windows
flutter run -d <android-device-id>
```

本地功能不依赖 Supabase。测试云端备份时使用专门的测试令牌，不要在日志或提交中暴露个人令牌。

## Windows 构建和发布

Flutter release 构建：

```powershell
flutter build windows --release
```

当前发布方式：

1. 构建 Windows release bundle。
2. 使用 Inno Setup 6 将产物制作成 EXE 安装包。
3. 上传到 GitHub Releases。
4. Release tag 使用可被 `pub_semver` 解析的语义版本，通常为 `vX.Y.Z`。

当前仓库没有 Inno Setup 脚本，因此安装路径、升级覆盖、卸载数据保留和快捷方式规则尚不可复现。应把 `.iss` 脚本纳入版本控制，并建立发布清单。

## Android 构建和发布

当前发布产物是 APK：

```powershell
flutter build apk --release
```

正式发布前的阻塞项：

- `applicationId` 仍为 `com.example.dndtoolkit_flutter`。
- release build 当前使用 debug signing。
- 没有受控的 release keystore 配置和密钥注入说明。
- Android 最低版本没有在产品支持矩阵中明确固定。

在这些问题解决前，不应把构建产物视为成熟的长期升级通道。签名密钥不得提交到仓库。

## 版本和更新检查

应用版本来自 `pubspec.yaml` 的 `version: major.minor.patch+build`。

`UpdateService`：

- 读取当前 package version。
- 请求 GitHub API 的 `/releases/latest`。
- 去除 tag 中的 `v` 后按 semantic version 比较。
- 有新版本时显示红点和 Release notes。
- 用户点击后在外部浏览器打开 Release 页面。
- 网络错误在静默检查时不提示，也不影响应用使用。

当前没有应用内下载、校验、安装或回滚。应用内更新属于路线图项目；实现时必须分别设计 Windows 安装器和 Android APK 的安全升级流程。

## 配置与秘密

- Supabase URL 和 publishable/anon key可以随客户端发布。
- 用户身份令牌不能硬编码、提交或打印。
- Android keystore、密码和签名配置不能提交。
- 测试文件必须脱敏，不得包含真实角色数据或个人文件路径。

## 依赖升级

升级依赖时：

1. 阅读目标 package 的迁移说明。
2. 优先单独提交锁文件和必要适配，避免混入功能改动。
3. 运行 `flutter analyze`、完整测试和两端 release 构建。
4. 特别验证文件 picker、分享、PDF、path provider、Supabase 和 package info 等平台插件。
5. 不因存在 iOS/macOS/Linux/Web 目录而为非支持平台投入兼容工作，除非明确改变平台决策。

## 发布前检查

- 版本号和 GitHub tag 一致。
- Release notes 描述数据格式或兼容变化。
- 旧 JSON、PDF 导入和云备份恢复回归通过。
- Windows 10/11 目标环境手工验证。
- 至少一个最低支持 Android 版本和一个较新版本设备验证。
- 无真实令牌、个人路径或隐私数据进入产物/日志。
- 安装、覆盖升级、卸载和本地数据保留行为经过验证。
- GitHub Release 资产链接可访问，应用更新提示可正确跳转。
