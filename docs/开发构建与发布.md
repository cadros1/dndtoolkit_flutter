# 开发、构建与发布

## 当前工具链约束

- Flutter：stable channel 项目；实际使用版本应以 `flutter --version` 和 `.metadata` 为准。
- Dart SDK：`pubspec.yaml` 要求 `^3.10.1`。
- Android Java/Kotlin target：Java 17。
- Node.js 只用于 Husky 与 commitlint，不参与 Flutter 运行时。
- 依赖版本以 `pubspec.lock` 和 `package-lock.json` 为可复现基线。

不要只依据 README 中宽泛的“Flutter 3.x”判断兼容性。

### 已验证的 Windows 开发环境

截至 2026-08-13，本项目已在以下组合完成环境诊断、完整测试和双平台 release 构建：

- Flutter 3.38.3 stable、Dart 3.10.1。
- Windows 11、Visual Studio Community 2022 17.14，包含 Windows 桌面 C++ 工具链。
- Android SDK 35、Android platform 36、JDK 21；项目仍以 Java 17 为编译 target。
- VS Code 1.133.0，Dart 与 Flutter 扩展 3.140.0。

版本号是一次验证快照，不是升级授权。后续环境不同或依赖升级时，应先重新运行 `flutter doctor -v`，再依据实际退出码判断兼容性。当前开发机配置了 Flutter/Pub 国内镜像，因此 CLI 输出镜像来源提示属于正常环境信息，不等同于下载失败。

## VS Code 与 Codex 项目配置

- `.vscode/extensions.json` 推荐官方 Dart 与 Flutter 扩展。
- `.vscode/settings.json` 将 `build/`、`.dart_tool/` 和 `node_modules/` 排除在文件监控、搜索和 Dart 分析之外。这些目录可在构建或 Widget Preview 后增长到数 GB；不排除时会放大 `workspaceContains` 扫描、文件监听和分析服务负担。
- `.codex/rules/default.rules` 只允许日常低风险命令在沙箱外运行，包括环境诊断、依赖恢复、项目清理、格式化、代码生成、静态分析、测试和 Windows/Android 构建。规则是项目级配置，只有仓库被 Codex 标记为 trusted 时才加载，新增或修改规则后需要重启 Codex。
- 规则刻意不放行 SDK/依赖升级、`flutter precache`、任意 Dart 脚本及全局配置修改；这些操作仍应逐次审查。

Flutter SDK、Pub 缓存和 Dart/Flutter 用户工具状态通常位于仓库之外。Codex 的 `workspace-write` 沙箱账户无法写入这些位置，因此沙箱内可能出现 SDK 缓存拒绝访问、用户工具状态拒绝访问或 Git `dubious ownership`。这类错误发生在测试进程启动之前，不代表测试超时或 Flutter 工具缺失。处理顺序是：

1. 保留并检查实际错误输出，确认失败发生在 SDK/缓存初始化阶段。
2. 对命中精确规则的命令改在宿主环境执行，不要通过放宽整个沙箱、全局修改目录所有权或添加宽泛的 `flutter`/`dart` 白名单规避。
3. 使用 `AGENTS.md` 中的超时基线等待真实退出码；首次依赖解析、代码生成、静态分析和全量编译可能长时间没有中间输出。

若 VS Code 再次弹出 Flutter/Dart 错误，先检查当前会话的 Dart LSP、Flutter daemon 和 extension host 日志，并按扩展 ID 归因。extension host 中其他扩展的激活扫描超时不等于 Dart/Flutter 插件失败。不要因为一次 DTD/LSP 断连就长期关闭相关功能；应先用新窗口冷启动复现，并确认工作区排除配置已经加载。

## 初始化

```powershell
flutter --version
flutter doctor -v
flutter pub get
npm install
```

如果只修改 Flutter 代码且 Husky 已安装，通常不需要重复执行 `npm install`。

## 代码生成

`lib/models/character.g.dart` 由 `json_serializable` 生成：

```powershell
dart run build_runner build --delete-conflicting-outputs
```

修改 `@JsonSerializable` class、构造参数或 `@JsonKey` 后必须重新生成并检查 diff。禁止手工修补 `.g.dart`。

```powershell

```

本地功能不依赖 Supabase。测试云端备份时使用专门的测试令牌，不要在日志或提交中暴露个人令牌。

## Windows 构建和发布

AI 服务 API Key 使用 `flutter_secure_storage_windows`。Windows 开发机除“使用 C++ 的桌面开发”外，还必须安装与当前 Visual Studio 工具链匹配的 ATL 组件；缺少时会在插件编译阶段报 `atlstr.h` 不存在。

Flutter release 构建：

```powershell
flutter build windows --release
```

当前发布方式：

1. 构建 Windows release bundle。
2. 使用 Inno Setup 6 将产物制作成 EXE 安装包。
3. 上传到 GitHub Releases。
4. Release tag 使用可被 `pub_semver` 解析的语义版本，通常为 `vX.Y.Z`。

当前仓库没有 Inno Setup 脚本，因此安装路径、升级覆盖、卸载数据保留和快捷方式规则尚不可复现。应把 `.iss` 脚本纳入版本控制，并建立发布清单。

## Android 构建和发布

当前发布产物是 APK：

```powershell
flutter build apk --release
```

本项目可能与 Windows 用户级 Pub 缓存位于不同盘符。Kotlin 增量编译会尝试把 Pub 插件源码相对化到 Android 项目根目录；跨盘时会报 `this and base files have different roots`，继而出现 `Could not close incremental caches` 或 Kotlin daemon 异常。Gradle 有时会回退并最终成功生成 APK，但大段异常会掩盖真实构建结果。

为避免该已复现问题，`android/gradle.properties` 固定设置：

```properties
kotlin.incremental=false
```

这会牺牲部分 Kotlin 增量编译收益，但不会关闭 Gradle 的其他构建缓存。除非已在跨盘环境验证新版 Kotlin Gradle Plugin 修复了路径问题，否则不要删除该配置。判断构建成功与否以最终退出码和 `Built ...app-release.apk` 为准；第三方插件产生的 Java 8 target 或 Android deprecated API warning 本身不是构建失败。

默认产物位置：

- Windows：`build/windows/x64/runner/Release/dndtoolkit_flutter.exe`
- Android：`build/app/outputs/flutter-apk/app-release.apk`

正式发布前的阻塞项：

- `applicationId` 仍为 `com.example.dndtoolkit_flutter`。
- release build 当前使用 debug signing。
- 没有受控的 release keystore 配置和密钥注入说明。
- Android 最低版本没有在产品支持矩阵中明确固定。

在这些问题解决前，不应把构建产物视为成熟的长期升级通道。签名密钥不得提交到仓库。

## 版本和更新检查

应用版本来自 `pubspec.yaml` 的 `version: major.minor.patch+build`。

`UpdateService`：

- 读取当前 package version。
- 请求 GitHub API 的 `/releases/latest`。
- 去除 tag 中的 `v` 后按 semantic version 比较。
- 有新版本时显示红点和 Release notes。
- 用户点击后在外部浏览器打开 Release 页面。
- 网络错误在静默检查时不提示，也不影响应用使用。

当前没有应用内下载、校验、安装或回滚。应用内更新属于路线图项目；实现时必须分别设计 Windows 安装器和 Android APK 的安全升级流程。

## 配置与秘密

- Supabase URL 和 publishable/anon key可以随客户端发布。
- 用户身份令牌不能硬编码、提交或打印。
- Android keystore、密码和签名配置不能提交。
- 测试文件必须脱敏，不得包含真实角色数据或个人文件路径。

## 依赖升级

升级依赖时：

1. 阅读目标 package 的迁移说明。
2. 优先单独提交锁文件和必要适配，避免混入功能改动。
3. 运行 `flutter analyze`、完整测试和两端 release 构建。
4. 特别验证文件 picker、分享、PDF、path provider、Supabase 和 package info 等平台插件。
5. 不因存在 iOS/macOS/Linux/Web 目录而为非支持平台投入兼容工作，除非明确改变平台决策。

## 发布前检查

- 版本号和 GitHub tag 一致。
- Release notes 描述数据格式或兼容变化。
- 旧 JSON、PDF 导入和云备份恢复回归通过。
- Windows 10/11 目标环境手工验证。
- 至少一个最低支持 Android 版本和一个较新版本设备验证。
- 无真实令牌、个人路径或隐私数据进入产物/日志。
- 安装、覆盖升级、卸载和本地数据保留行为经过验证。
- GitHub Release 资产链接可访问，应用更新提示可正确跳转。
